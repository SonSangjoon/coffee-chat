# Coffee Chat Generic Engine v1 Implementation Plan

> **For Codex:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` to execute this plan task by task. For every behavior change, use `superpowers:test-driven-development`; before declaring completion, use `superpowers:verification-before-completion`.

**Goal:** Finish `coffee-chat` as a neutral, installable engine/template that can atomically initialize a separate downstream checkout as a self-contained public temporal-KG instance, without shipping Son or any other person's knowledge in the engine.

**Architecture:** `coffee-chat.json` is a strict discriminated manifest. The maintained repository stays `repository_role: "engine"` and generates only a knowledge-free plugin plus documentation Pages. A Candidate may convert an explicitly fingerprinted downstream engine checkout into `repository_role: "instance"`; only that instance owns Profile, Notes, Entities, index, namespaced plugin snapshot, and KG Pages. Canonical knowledge and deterministic projections remain separate, while Derived Perspective and Task Lens exist only during agent use.

**Tech Stack:** Node.js 24.5.0, npm 11.5.1, TypeScript 7.0.2, Vitest 4.0.18, Astro 7.1.6, Cytoscape 3.34.0, `@types/cytoscape` 3.31.0, Playwright 1.62.1, Ajv 8.17.1, YAML 2.8.1. Use one root ESM package and exact lockfile entries.

**Normative contract:** `docs/superpowers/specs/2026-07-30-coffee-chat-design.md`

## Non-negotiable boundaries

- The engine root has no `profile`, `time_zone`, `knowledge/`, personal plugin namespace, personal snapshot, or personal Pages.
- The stable engine plugin and marketplace names are `coffee-chat` and `coffee-chat-marketplace`.
- Son's Taste/Iteration material is input-only under `tests/fixtures/son-input/`. Tests may materialize it only in an external temporary repository, must not snapshot generated bytes, and must remove the temporary repository after assertions.
- Package and Pages tests use a fictional synthetic instance. Their generated output lives outside the checkout and is classified `ephemeral-test`; release and upload entry points reject that class.
- Structural validation may reject unsafe or inconsistent data, but must not score meaning, count evidence as confidence, or persist a POV, Mental Model, Derived Perspective, or Task Lens.
- Every task follows red -> observed expected failure -> smallest implementation -> focused green -> broader green -> commit. Never weaken an assertion merely to obtain green.
- No task commits, pushes, opens a PR, enables Pages, or edits a GitHub ruleset unless its step explicitly says so.
